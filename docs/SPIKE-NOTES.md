## 2026-08-15 — Phase 0 gate PASSED: disk image boots in stock apple2js.html

Verified `PrinceOfPersia_5.25_SideA.nib` in an unmodified clone of whscullin/apple2js (`.scratch/apple2js`, not committed), served via its own `npm run dev` webpack-dev-server, loaded via apple2js's URL-hash disk-loading feature: `apple2js.html#http://localhost:8080/pop-test-sideA.nib`.

**Method note:** apple2js's run loop is driven by `requestAnimationFrame`, which this automated browser session throttled to a near-standstill (2 CPU cycles executed after several seconds). Worked around this by driving the CPU directly from the console — `cpu.stepCycles(n)` + `io.tick()` in a loop, then `vm.blit()` to force a render — which exercises the exact same assembler output and disk-reading code paths without depending on the browser's rAF scheduling. This is a testing-harness workaround, not a change to the emulator itself, and doesn't affect the real deployed site (a real browser tab in normal use runs rAF fine).

**Result, sampled via `window.Apple2.apple2` (the `main2.ts`/`entry2.ts` legacy non-React entry point that `apple2js.html` actually uses — not the React `App`/`Apple2.tsx` component, which is a separate entry point):**
- CPU started at PC `$FA62`, inside the Apple II system monitor ROM ($F800–$FFFF) — the boot ROM's disk-read routine, as expected immediately after reset.
- After ~26M stepped cycles (~26 emulated seconds), PC settled at `$0985` — well outside ROM, in RAM — and stayed rock-stable there across further sampling out to 41M+ cycles. This is a clean handoff: the boot ROM successfully read track 0 side A of our RW18-format image and jumped into the loaded Prince of Persia boot code, which ran further (decompression/disk-read routines) before settling into a wait loop.
- Canvas pixel inspection went from 0% non-black (blank boot screen) to a stable 0.6% non-black with real white content — rendered a single line of text on an otherwise blank hi-res screen (confirmed via a coarse ASCII render of the framebuffer showing one line of readable text, roughly a third of the way down the screen).
- This matches, exactly, adamgreen's documented behavior for this build configuration (`Notes/pop-build.creole`): *"When playing from 5.25" disks, you will get the following message when it is necessary to switch sides of the disk, 'Insert Prince of Persia Disk'... I have left the code configured to build for 3.5" disks so it displays this message instead."* We loaded only Side A alone into a single drive with no Side B available, so this "insert disk" prompt is exactly the expected outcome, not a bug.

**Conclusion:** the assembled disk image is a genuine, correctly-functioning Prince of Persia boot disk — real 6502 code from the source assembly executed, read further data off the image, and produced the exact documented on-screen behavior. Phase 0's pass/fail gate is met. Also confirmed in passing: `Apple2` (top-level class in `js/apple2.ts`) implements `getState()`/`setState()` covering CPU, video, IO, MMU, and RAM bank state — this is a strong head start for Phase 3 (rewind/save), worth revisiting when that phase starts.

**Bonus finding:** `@whscullin/cpu6502` (apple2js's CPU core) is already published as its own separately-versioned submodule package (`submodules/cpu6502`), which may simplify Phase 1's "vendor a subset of apple2js" plan — worth checking whether it and `apple2shader` can be depended on directly rather than manually extracting files.

## 2026-08-16 — Caught a production-build-only breakage before it reached Phase 5's deploy config

`vite dev` (used for all Phase 1-3 testing) resolves any import path live from disk, which masked a real bug: apple2js's ROM loading (`import(`./roms/system/${options.rom}`)`, extensionless dynamic import) can't be statically analyzed by Rollup's dynamic-import-vars handling, which hard-requires a file extension in the static part of the template — with no config escape hatch (confirmed by trying `@rollup/plugin-dynamic-import-vars` directly with various options; it errors outright rather than warning). A plain `npm run build` completed with 0 errors and looked fine, but `vite preview` (serving the actual `dist/` output, i.e. what Azure Static Web Apps would actually serve) showed the real symptom: 404s on `/assets/roms/system/fpbasic` and a hard `Failed to fetch dynamically imported module` error — the game would not have booted at all once deployed, despite every dev-mode test passing.

**Fix:** a small Vite plugin (`apple2RomImportExtensionFix` in `web/vite.config.ts`) rewrites just those two import expressions in-memory as `apple2.ts` is transformed (`enforce: 'pre'`, runs before dynamic-import-vars sees the code) — appends `.ts` to the static template part. The vendored submodule file on disk is never touched (keeps `git submodule update` and upstream diffing clean). The plugin throws loudly if the expected source patterns aren't found, so an upstream apple2js change that alters this code won't silently regress back to the broken behavior.

**Verified:** `npm run build` now produces separate hashed chunks per ROM (`fpbasic-*.js`, `apple2_char-*.js`, etc., 19 total). `vite preview` boots the game correctly — confirmed via the same PC-address check as every other phase (`$0985`), this time reached via real `requestAnimationFrame` ticks (no manual `stepCycles` workaround needed — this tab happened to get real rAF scheduling), the strongest boot confirmation yet since it exercised the actual unmodified emulator run loop rather than a testing workaround.

**Lesson for later phases:** `vite dev` is not sufficient to validate a change is deploy-safe. Any future change touching the emulator core, ROM loading, or build config should be checked against `vite build` + `vite preview`, not just dev mode, before being considered done.

Next: Phase 5 (Azure Static Web Apps deployment) — repo-side config is done (`staticwebapp.config.json`, `.github/workflows/azure-static-web-apps.yml`); provisioning the actual Azure resource and adding the deployment token secret is a manual step for the user, documented in README.

## 2026-08-16 — Bug: booted as the wrong Apple II model, POP rejected it

User-reported symptom: on boot, the screen showed "requires a //c or //e with 128K" instead of the game. Root cause: `EmulatorController.ts` was modeled on apple2js's `js/main2.ts` legacy entry point, which targets a **plain Apple II / II+** (`e: false, enhanced: false, rom: 'fpbasic'`) — but POP's `BOOT.S` does an explicit 128K memory check (per its Code Museum description: "two-stage disk boot loader with 128K memory check") and correctly refuses to run on that profile, since a plain II/II+ tops out at 64K.

This was missed by every prior verification pass because they all checked *that the CPU transferred control into loaded RAM code and something rendered* (PC address + non-black-pixel percentage), not *what the rendered text actually said* — the checks couldn't distinguish "showing the game" from "showing a rejection message," since apple2js's own `js/main2.ts` example that all this was modeled on has exactly the same limitation (it also defaults to a plain II, not a 128K machine) and was never actually meant to run something that requires 128K.

**Fix:** switched `EmulatorController.ts` to the Enhanced Apple //e, 128K profile (`e: true, enhanced: true, rom: 'apple2enh', characterRom: 'apple2enh_char'`) — matching apple2js's own default system profile (`js/components/util/systems.ts`, `defaultSystem`) and its other legacy entry point, `js/main2e.ts`, which is the one actually meant for a 128K machine. Also dropped the `LanguageCard` slot-0 wiring (not used in `main2e.ts` either — the //e's own MMU provides 128K of bank-switched RAM natively, a physical language card is a II/II+-only concept) and set `SmartPort`'s `block` option to `false` to match `main2e.ts`'s enhanced-mode wiring.

**Verified:** rebuilt and re-checked via `vite preview` (not just `vite dev` — see the production-build lesson above). The framebuffer went from a single line of text (the rejection message) to a fully bordered, multi-line screen with real structured content — consistent with an actual title/menu screen rather than an error message. Not confirmed via literal OCR (no tool available to read on-screen text directly), but the qualitative change (single terse line -> full bordered screen with several lines of content) is strong evidence the memory check now passes and the game proceeds into real content.

## 2026-08-16 — Follow-up bugs found via user playtesting: wrong movement keys, forced keyboard mode

User playtest surfaced two more issues past the boot fix:

1. **"Constantly runs into the left wall, can't control the character"** — apple2js initializes all four simulated paddles to `0.0` (the extreme low end of its 0-1 range; 0.5 is center — confirmed against `js/ui/gamepad.ts`'s own real-gamepad math). With no physical gamepad connected in a browser session, that reading never changes, so POP's joystick-reading routine (`PREAD` in `GRAFIX.S`) saw a permanently-pushed-left stick. Fixed by centering all four paddles (`io.paddle(n, 0.5)`) right after boot in `EmulatorController.ts`. Confirmed via the running instance's internal `_paddle` state: `[0.5, 0.5, 0.5, 0.5]`.

2. **"I/J/K/M don't move the character"** — checked the real key bindings directly in `SPECIALK.S`: `kleft="j", kdown="k", kright="l", kup="i"` (plus diagonals `kupleft="u"`, `kupright="o"`) — it's I/J/K/**L**, not M. Also found `ksetkbd`/`ksetjstk` (Ctrl+K / Ctrl+J) toggle between keyboard and joystick input modes via a RAM flag, `joyon`.

Per explicit user request ("always force keyboard controls"), rather than relying on the player pressing Ctrl+K once (which only works if the game happens to poll the keyboard at that exact moment, and doesn't protect against anything switching back to joystick mode later), `joyon`'s resolved address was pulled from the assembler's list file for this exact build (`build-tooling/pop-build/obj/SPECIALK.LST`: `020D: 00  445 joyon ds 1`) and is now force-written to `0` every single frame via `forceKeyboardControls()` in `EmulatorController.ts`, called from `main.ts`'s tick callback. Verified: manually flipping the flag to `1` via the console got reverted to `0` within the next couple of frames on its own.

**Caveat:** `JOYON_ADDRESS` is resolved from this specific compiled binary's list file, not derived symbolically — if `web/public/disks/*` is ever rebuilt from source with a different layout, this address needs re-checking against the regenerated `.LST` file.

## 2026-08-16 — Third playtest bug: Rewind/Continue leaves stale background pixels

User report: after Rewind or Continue, the screen doesn't fully repaint — only the player sprite (redrawn every frame by its own animation code) looks right; the static room background is left stuck with whatever was on screen before the restore.

**Root cause**, found by reading `js/canvas.ts` and `js/ram.ts`: `HiresPage2D`/`LoresPage2D` (the hi-res/lo-res video renderers) don't hold their own copy of pixel memory — they get it via `ram.getBuffer(start, end)` (`js/ram.ts`), which is `this.mem.subarray(...)`, a *view* sharing the same underlying `ArrayBuffer` as the RAM bank's own `mem`, taken once at construction. But `RAM.setState()` (used by every restore, since `Apple2.setState()` restores each RAM bank via this) does `this.mem = new Uint8Array(state.mem)` — reassigning to a **brand-new** array rather than copying into the existing one. That severs the aliasing: the restored pixel bytes land correctly in the new `RAM.mem`, but the video renderer's buffer view still points at the old, orphaned array and never sees them. Nothing re-establishes the link afterward (no code anywhere calls `getBuffer()` again post-restore) — so the background stays stuck at pre-restore content indefinitely, while newly-drawn content (the sprite) looks fine because it's written through the *current* live buffer object on each new frame, not through the restored-but-disconnected one.

**Fix:** same in-memory Vite-transform pattern used for the ROM dynamic-import fix (`apple2RamAliasingFix` in `web/vite.config.ts`) — rewrites `RAM.setState()`'s body from `this.mem = new Uint8Array(state.mem)` to `this.mem.set(state.mem)` (in-place copy) as `js/ram.ts` is transformed, without touching the vendored file on disk. Preserving the array's identity means any `subarray()` view aliased into it — hi-res pages today, anything else that does the same thing in the future — stays automatically in sync, rather than patching each aliasing site individually.

**Verified** via direct object-identity check in the console: `apple2.ram[0].mem.buffer === apple2.hgr._buffer[0].buffer` — `true` both before and after a `setState()` round-trip. Under the old (buggy) reassignment behavior this would read `false` after restore (a fresh `Uint8Array(...)` copy always gets a new backing `ArrayBuffer`); observing `true` confirms the aliasing — and therefore the video buffer's sync with restored RAM — survives the restore. `apple2.getVideoModes().setState()` (called as part of `Apple2.setState()`) already triggers a full-screen `refresh()` internally on every restore, so once the buffer itself is correct, the existing refresh call now has correct data to actually paint.

## 2026-08-16 — Feature request from playtesting: bigger rewind, quick-rewind button, multi-save, and a real focus bug

User asked for four things after more playtesting: a 5-minute rewind buffer (was ~1-2 min), a discrete "rewind 10 seconds" button alongside the scrubber, multiple named localStorage saves with a save/load menu (was one fixed slot), and looked into a keyboard-stops-responding-after-rewind/continue issue they'd noticed ("not sure if it lost focus or I had to do ctrl+k").

**Measured real snapshot cost before sizing anything:** a raw (unencoded, in-memory) `Apple2.getState()` is ~451KB — not the couple-hundred-KB ballpark assumed in the original plan. Breakdown: ~233KB is the loaded disk's nibble data (35 tracks × 6656 bytes — the *entire* disk image, since `DiskII`'s own `getState()` includes it), ~166KB is RAM/aux-RAM banks, and (worth knowing, not worth fixing) apple2js's own `State` shape double-counts each RAM bank — the same bytes appear once under `state.ram[]` and again under `state.mmu.mem00_BF[]`, since `MMU` just holds the same `RAM` objects and each `getState()` call makes an independent copy. Didn't touch that redundancy — deduplicating it would mean patching `Apple2`/`MMU`'s own state shape, more risk than it's worth for a rewind buffer that's already within a safe memory budget at the sizing below.

**Rewind buffer, `web/src/emulator/snapshot/RewindBuffer.ts`:** switched from frame-counting to wall-clock timestamps per entry (`RewindEntry { timestamp, state }`) — frame-counting ties rewind depth to actual fps, which this whole project has repeatedly seen vary a lot (rAF throttling in automated/backgrounded tabs). 5 minutes at a 5-second snapshot interval = 60 entries × ~451KB ≈ 27MB peak — a reasonable budget (a 1-second interval would be 300 entries ≈ 135MB, into risky territory on constrained devices, hence 5s not 1s). `RewindBuffer.indexSecondsAgo(n)` finds the entry closest to (newest − n seconds) for the new discrete rewind button, independent of the scrubber's index-based UI.

**10-second rewind button:** `attachRewindButton()` in `RewindScrubber.ts`, same stop/restore/run pattern as the scrubber, just jumping straight to `indexSecondsAgo(10)` instead of following slider drag. Verified with a synchronous before/after cycle-count check (no round-trip delay to let the emulator run forward and mask the result): clicked, and the CPU's cycle count immediately matched the target snapshot's exactly.

**Root cause of the focus bug:** clicking any button or dragging the range slider moves DOM focus onto that element — completely ordinary browser behavior, but keyboard input is only wired to the `<canvas>` element (`emulator/keyboard.ts`), so once focus moved away, physical keypresses stopped reaching the game until something refocused the canvas. The user's Ctrl+K wasn't fixing anything about keyboard-mode state (that's already force-set every frame, unrelated) — whatever incidental click came with it was what actually refocused the canvas. Fixed by explicitly calling `canvas.focus()` after every state-restoring interaction: the rewind scrubber's `pointerup`, the new 10s button, and — for the save/load dialogs — a `close` event listener on each `<dialog>` (covers ESC-dismissal too, not just explicit button clicks, since `HTMLDialogElement`'s native `close` event fires for both).

**Multi-save, `SaveGameStore.ts` rewrite:** was a single fixed `localStorage` key; now an index (`pop-assist:saves-index:v1`, an array of `{id, name, savedAt}`) plus one `localStorage` entry per save (`pop-assist:save-data:v1:<id>`). Saving under a name that already exists overwrites that entry (same id, refreshed timestamp) rather than creating a duplicate. `saveGame()` catches `localStorage.setItem` failures (quota exceeded — realistic after a handful to a couple dozen saves at a few hundred KB each, given the browser's typical 5-10MB per-origin cap) and throws a descriptive error rather than silently failing or corrupting the index.

**Save/Load UI, `web/src/ui/SaveMenu.ts`:** two native `<dialog>` elements (`#save-dialog`, `#load-dialog` in `index.html`) — a name-prompt form (prefilled with a formatted timestamp, editable) and a list of existing saves each with Load/Delete buttons. Delete re-renders the list in place without closing the dialog. No framework — same hand-rolled DOM style as the rest of the UI.

**Verified end-to-end in the browser**, not just by reading the code back: saved two distinctly-named games, confirmed both persisted correctly and independently in `localStorage`; loaded one back and confirmed via CPU cycle count that it actually restored to the saved point (not just closed the dialog); deleted both and confirmed the list and `localStorage` index emptied correctly; confirmed canvas regains keyboard focus after every one of these interactions via `document.activeElement` checks.

## 2026-08-16 — Sound

User asked whether the original sound could be implemented — it wasn't wired up at all yet (`EmulatorController.ts` only ever set up disk/smartport, no audio). apple2js already has a complete Web Audio-based sound engine (`js/ui/audio.ts`'s `Audio` class + `js/ui/audio_worker.ts`'s `AudioWorkletProcessor`) that just needed constructing — `new Audio(io)`, same as apple2js's own `main2e.ts` does. `Apple2IO`'s speaker-toggle emulation (driven by SOUND.S's writes to the `$C030` soft switch) was already running underneath the whole time; nothing downstream of that existed to turn it into actual audio output.

`Audio` itself already listens for the first `keydown`/`mousedown`/`touchstart` to resume the `AudioContext` (the standard browser autoplay-policy workaround) — no extra wiring needed there, it lines up naturally with the existing click-canvas-to-focus interaction.

**Verified in the browser**, two ways: (1) console showed `Sound initialized` and `AppleAudioProcessor constructor` — confirming the worklet module actually loaded and its processor constructed inside the AudioWorkletGlobalScope, not just that our code ran without throwing; (2) monkey-patched `audio.workletNode.port.postMessage` to count calls — 4,836 sample-data messages posted across 6 seconds of real gameplay, confirming actual audio sample data is flowing continuously, not just an idly-running-but-silent `AudioContext`. Exposed `window.__audio` alongside the existing `__apple2`/`__rewindBuffer` debug handles for this and future checks.

## 2026-08-16 — Audio stutter, caused by the rewind feature itself

User reported the sound "pulsing... not steady... a stutter" right after sound started working. Root cause: `apple2.ts`'s `run()` loop calls `Apple2IO.tick()` (which generates audio samples) and `this.tick()` (our own callback — `forceKeyboardControls`, `RewindRecorder.onTick()`, `scrubberHandle.syncRange()`) back to back in the *same* synchronous `requestAnimationFrame` callback, then schedules the *next* rAF call. `RewindRecorder.onTick()` was, every 5 seconds, synchronously calling `captureSnapshot()` + `captureThumbnail()` right there — measured at ~11ms (~1ms state copy, ~10ms PNG-encoding the thumbnail). At a 60fps ~16.7ms frame budget, that's over half the frame gone to work with nothing to do with audio, delaying the next frame's `io.tick()` call by a similar amount — an audible gap in sample generation, recurring exactly on the 5-second snapshot interval. That periodicity is what made it read as "pulsing" rather than random crackle.

**Fix:** `RewindRecorder.onTick()` (`RewindBuffer.ts`) now only does the cheap timestamp check synchronously; the actual capture is deferred via `setTimeout(..., 0)` to a separate macrotask, so it runs after the current frame (and the next rAF scheduling) has already happened. The few-millisecond timing skew this introduces is irrelevant at 5-second snapshot granularity.

**Verified:** rewind buffer still populates correctly with valid thumbnails after the change (no functional regression), and re-ran the same audio-sample-flow check as the initial sound verification — comparable throughput (4,509 messages/6s vs. 4,836/6s before), confirming audio delivery wasn't broken by the fix. Couldn't directly confirm the *perceptual* fix (no way to listen to audio from this environment) — worth the user confirming the stutter is actually gone, not just that the mechanism causing it was removed.

## 2026-08-16 — Solved: the disk-swap limitation that blocked real gameplay since Phase 0

User asked directly: get past the disk swap and let the game actually be played. This had been a known, repeatedly-noted limitation since Phase 0 — every verification in this whole project up to now was against a game stuck at (or just past) the "Insert Prince of Persia Disk" prompt, never real dungeon gameplay.

**First attempt: boot from the 3.5"/SmartPort image instead of the 5.25" pair.** `POPBOOT35.S`/`popboot35` is a dedicated boot loader for the `.hdv` image, self-contained as a single volume, so in principle it shouldn't need any side-swap at all. Generalized `EmulatorController.ts`'s disk-loading (`loadDiskFromUrl` split into that plus a new `loadBlockImageFromUrl`, both thin wrappers around fetch + the respective card's `setBinary` — `DiskII` and `SmartPort` share a `MassStorage<T>` interface in apple2js) and pointed `main.ts` at `PrinceOfPersia_3.5.hdv` via the `SmartPort` card instead. Booted with no errors, but landed on a completely blank, unresponsive screen — worse than the 5.25" path, not better. Most likely cause: apple2js's `SmartPort` emulation doesn't fully implement whatever specific protocol sequence `POPBOOT35` expects; not investigated further given the second approach below worked. Reverted this attempt (back to 5.25"/`DiskII`), but kept `loadBlockImageFromUrl` and the `SmartPort` card wiring in place — harmless, and useful if the `.hdv` path is worth revisiting later.

**Second attempt, successful: automatic disk-side-swapping.** Found the actual mechanism by reading `Notes/pop-codereview-diskreads.creole` — adamgreen's own prior analysis of exactly this code (a research shortcut worth remembering for future questions about this source: check `build-tooling/pop-build/Notes/*.creole` before re-deriving something from scratch). The disk driver (`RW1835.POP.S`, called from `MASTER.S`) sets a flag, `BBundID`, to `POPside1` ($A9) or `POPside2` ($AD) before each read depending on which physical side the data lives on; on a real machine the read simply fails until the player flips the disk to match, and the driver's own retry loop (`jsr error` / `jmp :test`) just keeps trying against whatever's currently in the drive.

Resolved `BBundID`'s address the same way as every other memory-address dependency in this project: `build-tooling/pop-build/obj/MASTER.LST` → `03F5: 00  464 BBundID ds 1` (immediately after `level` at `$03F4`, both from the same `EQ.S` `DUM` block).

New module, `web/src/emulator/diskSwap.ts` (`attachAutoDiskSwap`): watches `BBundID` every tick, and the instant it no longer matches whichever side is currently loaded in `DiskII` drive 1, swaps in the other side's pre-fetched `nib` buffer via `setBinary()` — before the driver's retry even needs to succeed on its own. Also nudges a harmless keypress through afterward (`io.keyDown(0x0d)` / `keyUp()`) as a safety net, in case the driver's error/prompt path turns out to be gated on a keypress rather than a tight loop (not fully confirmed by reading the source alone — `prompt` turned out to be a 3-byte data variable, not a traceable subroutine, so this was covered defensively rather than traced further). `main.ts` now prefetches both side `.nib` buffers once at boot (so mid-game swaps don't wait on a network round-trip) and drives `onTick()` from the same per-frame callback as everything else.

**Verified working, decisively, by watching real state transitions over time** — not just "no errors":
- `level` (the byte this project already reads for the Map tab) went `255` (uninitialized) → `0` ("demo", matching TOPCTRL.S's own comment: "0 for demo") → `1` ("1 for new game") after a keypress, exactly matching the source's documented meaning at each stage.
- The framebuffer went through three visibly distinct, increasingly complex states: a single line of text (the old "insert disk" prompt) → a rich, symmetric hi-res image that changed frame-to-frame on repeated sampling (real-time animation — the attract-mode demo actually playing) → a completely different brick/tile dungeon-room pattern once level hit 1 (real gameplay, not a title screen).
- Confirmed the game keeps running stably in this state: cycles and PC continued advancing smoothly across multiple samples, `isRunning()` stayed true, no hangs, no console errors, `level` held steady at `1` through a simulated keypress (held right/L) rather than reverting or crashing.

This is the first point in the whole project where the emulator has been confirmed to reach actual player-controlled dungeon gameplay, not just a boot/menu/prompt screen. Worth the user actually playing it now to confirm it *feels* right (physics/timing/collision) — everything verified here is CPU-state and framebuffer evidence from outside the game, not a substitute for actually playing it.
